## Modelagem do Processo de Negócio 

### Descrição Geral da Proposta

O CuidAí propõe centralizar essas informações em um aplicativo mobile único e colaborativo, permitindo que múltiplos cuidadores, sejam familiares, profissionais ou instituições, compartilhem o mesmo perfil de cuidados de um paciente. O projeto está limitado ao escopo Mobile First, com dados simulados localmente e sem backend real, conforme as restrições definidas.
As oportunidades de melhoria dos dois processos abaixo estão concentradas em dois pontos: (1) reduzir a dependência de canais informais, como WhatsApp, cadernos e quadros, para registrar e acompanhar tarefas; e (2) tornar a comunicação e a transição de informações entre os cuidadores mais rápida, padronizada e organizada.
Eu usaria exatamente essa versão no trabalho. 

## Requisitos

As tabelas que se seguem apresentam os requisitos funcionais e não funcionais que detalham o escopo do projeto. Para determinar a prioridade de requisitos, aplicou-se uma escala de *Alta, Média e Baixa* importância, onde:
* *Alta:* Funcionalidades essenciais (Core) sem as quais o sistema não atinge seu objetivo principal.
* *Média:* Funcionalidades importantes que agregam valor significativo, mas não impedem o uso básico do sistema.
* *Baixa:* Funcionalidades desejáveis, que melhoram a experiência, mas podem ser adiadas para versões futuras.

### Requisitos Funcionais

| ID     | Descrição do Requisito                                                                                             | Prioridade |
|--------|--------------------------------------------------------------------------------------------------------------------|------------|
| RF-001 | O sistema deve permitir a criação de contas de usuários, com funcionalidades de login e recuperação de senha.      | ALTA       |
| RF-002 | O sistema deve permitir o cadastro e o gerenciamento de perfis dos pacientes (idosos ou pessoas com deficiência).  | ALTA       |
| RF-003 | O sistema deve permitir o cadastro de contatos de emergência (médicos, ambulância, familiares próximos).           | ALTA       |
| RF-004 | O sistema deve permitir o cadastro de tarefas diárias, medicamentos e suas respectivas dosagens e horários.        | ALTA       |
| RF-005 | O sistema deve permitir o compartilhamento do perfil de cuidados e tarefas entre múltiplos usuários simultâneos.   | ALTA       |
| RF-006 | O sistema deve permitir que os cuidadores registrem a conclusão das tarefas, indicando quem as realizou e a hora.  | ALTA       |
| RF-007 | O sistema deve emitir notificações e alertas sobre os horários críticos de medicamentos e tarefas programadas.     | ALTA       |
| RF-008 | O sistema deve possuir uma agenda ou calendário para registro e acompanhamento de consultas médicas e exames.      | MÉDIA      |
| RF-009 | O sistema deve permitir o registro em formato de texto para intercorrências ou alterações nos sinais vitais.       | MÉDIA      |
| RF-010 | O sistema deve permitir que um administrador gerencie os níveis de permissão (ex: leitura ou edição de dados).     | MÉDIA      |
| RF-011 | O sistema deve gerar um resumo ou histórico diário facilitando a transição de turnos entre cuidadores.             | MÉDIA      |
| RF-012 | O sistema deve alertar os usuários sobre a necessidade de reposição de medicamentos com base no consumo registrado.| BAIXA      |

### Requisitos não Funcionais

| ID      | Descrição do Requisito                                                                                                           | Prioridade |
|---------|----------------------------------------------------------------------------------------------------------------------------------|------------|
| RNF-001 | O sistema deve ser um aplicativo móvel responsivo, compatível com os principais sistemas operacionais de smartphones do mercado. | ALTA       |
| RNF-002 | A interface de usuário deve ser simples, com fontes legíveis e alto contraste, visando atender pessoas com pouca familiaridade tecnológica. | ALTA       |
| RNF-003 | O sistema deve garantir a privacidade e segurança das informações médicas e pessoais registradas pelos usuários.                 | ALTA       |
| RNF-004 | O aplicativo deve processar as requisições do usuário (como transição de telas e registro de tarefas) em, no máximo, 3 segundos. | MÉDIA      |
| RNF-005 | O armazenamento e consumo de dados da aplicação deve utilizar uma arquitetura leve baseada em chamadas de API, garantindo agilidade. | MÉDIA      |

## Restrições

O projeto está restrito pelos itens apresentados na tabela a seguir.

| ID | Restrição                                                                                                                                                             |
|----|-----------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| 01 | O prazo de desenvolvimento e entrega do protótipo funcional é estritamente limitado ao encerramento do semestre letivo vigente.                                       |
| 02 | A arquitetura de dados deve ser suportada exclusivamente por uma API simulada localmente, vedando o desenvolvimento de um servidor backend real ou bancos em nuvem. |
| 03 | O sistema deverá focar inicialmente no desenvolvimento apenas para dispositivos móveis (Mobile First), sem previsão de versão Web ou Desktop neste ciclo do projeto.  |
| 04 | O projeto não possui orçamento alocado, obrigando a utilização exclusiva de ferramentas de desenvolvimento, design e prototipação de licenças gratuitas ou educacionais.|
| 05 | A equipe de desenvolvimento atua com carga horária parcial; em caso de desvios no cronograma, o escopo deve ser reduzido, sacrificando os requisitos de prioridade Baixa.|
