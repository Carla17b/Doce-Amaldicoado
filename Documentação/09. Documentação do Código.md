# Documentação da aplicação O Doce Amaldiçoado

## 1. Visão geral

A aplicação é um jogo narrativo de investigação desenvolvido para navegador. O usuário acessa o arquivo do caso, cria uma conta, entra no sistema e investiga uma mansão por meio de escolhas, objetos, evidências e interrogatórios.

O projeto é dividido em três partes principais. O **frontend** exibe as telas e controla a experiência do jogo. O **backend** recebe as solicitações de cadastro e login. O **banco de dados** armazena os usuários cadastrados.

A arquitetura utilizada é:

```
Navegador
   │
   ├── index.html  → estrutura das telas
   ├── css/style.css → aparência visual
   └── js/script.js → interações e regras do jogo
          │
          └── API HTTP do Flask
                  │
                  └── SQLite → doce_amaldicoado.db
```

## 2. Estrutura de pastas

```

├── app.py
```

O arquivo `doce_amaldicoado.db` é criado automaticamente pelo programa. Ele não precisa ser criado manualmente. Se ainda não houver cadastro, o arquivo pode existir com a tabela vazia.

A pasta `.venv`, quando criada no computador, contém o ambiente virtual do Python. Ela é usada apenas para instalar e executar as dependências e não faz parte da lógica da aplicação.

## 3. Arquivo `index.html`

O arquivo `index.html` define a estrutura visual da aplicação. Ele contém as telas do site público e as telas do jogo.

No cabeçalho, o HTML importa o arquivo de estilos:

```html
<link rel="stylesheet" href="css/style.css">
```

No final do documento, importa o JavaScript:

```html
<script src="js/script.js"></script>
```

### 3.1 Site público

O elemento com id `site` contém a apresentação inicial do caso. Essa parte mostra o título, o resumo da história, a vítima, os personagens e uma explicação da mecânica do jogo.

O botão `ir-entrar` leva o usuário para a tela de login. Se já existir uma sessão válida no servidor, o sistema pode abrir diretamente o menu da conta.

### 3.2 Tela de login

A seção `tela-login` possui os campos de e-mail e senha. O botão `btn-entrar` chama o backend para verificar os dados informados.

### 3.3 Tela de cadastro

A seção `tela-cadastro` possui os campos de nome, e-mail, senha e confirmação da senha. O botão `btn-cadastrar` envia os dados para a rota de cadastro da API.

### 3.4 Menu do usuário

A seção `tela-menu` apresenta o nome do usuário e opções para continuar a investigação, começar novamente, voltar ao arquivo público ou sair da conta.

### 3.5 Telas do jogo

As demais seções representam o prólogo, a mansão, cada cômodo, o mural de evidências, o interrogatório, a acusação e os finais possíveis. Elas ficam ocultas ou visíveis conforme a navegação controlada pelo JavaScript.

## 4. Arquivo `css/style.css`

O arquivo CSS controla a aparência do site. Ele define as cores, fontes, espaçamentos, botões, cartões, polaroides, mural de evidências, planta da mansão e comportamento responsivo.

As cores principais são armazenadas em variáveis CSS dentro de `:root`, por exemplo:

```css
:root {
  --noite: #0C1113;
  --papel: #DCD2BC;
  --lampada: #E0A94F;
}
```

A classe `.oculto` esconde telas que não estão ativas:

```css
.oculto {
  display: none !important;
}
```

As regras `@media` adaptam o layout para telas menores. Por exemplo, a área com duas colunas passa a ter apenas uma coluna em dispositivos estreitos.

O CSS também possui uma regra para reduzir animações quando o usuário ativou a preferência de acessibilidade `prefers-reduced-motion`.

## 5. Arquivo `js/script.js`

O JavaScript controla a maior parte do comportamento do jogo. Ele possui os dados dos personagens, as evidências, os cômodos, as escolhas, os interrogatórios, os finais e a comunicação com o backend.

### 5.1 Dados do jogo

As constantes `ELENCO`, `PISTAS`, `COMODOS`, `PERSONAS`, `PROLOGO`, `ACUSADOS` e `FINAIS` funcionam como estruturas de dados do jogo.

- `ELENCO` contém os personagens e os dados usados nos retratos.

- `PISTAS` contém o título, a origem e as interpretações de cada evidência.

- `COMODOS` define a planta da mansão e os objetos que podem ser examinados.

- `PERSONAS` define a personalidade, as respostas de reserva e as pistas associadas a cada suspeito.

- `PROLOGO` contém as cenas iniciais e as escolhas do jogador.

- `ACUSADOS` contém as opções disponíveis na etapa de acusação.

- `FINAIS` contém os cinco desfechos possíveis da história.

### 5.2 Estado da investigação

A função `novoJogo()` cria um novo estado para a investigação. Esse estado contém:

- evidências encontradas;

- evidências destruídas;

- objetos examinados;

- nível de medo;

- confiança em cada personagem;

- conversas realizadas;

- registro das ações;

- cena atual;

- suspeito selecionado;

- cômodo aberto;

- acusado escolhido;

- última tela visitada.

A variável `jogo` mantém o estado atual enquanto o usuário joga.

### 5.3 Navegação entre telas

A função `ir(t)` controla quais seções ficam visíveis. Ela adiciona ou remove a classe `oculto` e chama a função de desenho adequada para cada tela.

Por exemplo, ao navegar para `mansao`, a função chama `pintarMansao()`. Ao navegar para `suspeitos`, chama `pintarSuspeitos()`.

### 5.4 Cadastro e login

O frontend possui a função `api()`, que envia requisições HTTP para o backend e interpreta as respostas em JSON.

No cadastro, o JavaScript valida o nome, o formato do e-mail, o tamanho mínimo da senha e a confirmação da senha. Depois envia os dados para:

```
POST /api/cadastro
```

No login, envia o e-mail e a senha para:

```
POST /api/login
```

A sessão ativa é consultada por:

```
GET /api/sessao
```

O logout é realizado por:

```
POST /api/logout
```

O navegador não envia a senha diretamente para o banco. Ele envia a senha ao backend usando uma requisição HTTP, e o backend realiza a validação.

### 5.5 Salvamento do progresso

A função `salvar()` salva o progresso da investigação no `localStorage` do navegador. Isso é diferente do banco SQLite.

Atualmente, o banco de dados armazena apenas os dados da conta. O progresso do jogo permanece salvo localmente no navegador de cada usuário.

### 5.6 Investigação e evidências

A função `pintarMansao()` desenha a planta baixa da casa. Cada cômodo possui objetos que podem ser examinados.

A função `examinar()` registra o objeto como examinado, pode adicionar uma evidência ao mural e pode aumentar o nível de medo da casa.

A função `pintarMural()` mostra as evidências encontradas pelo jogador. Cada evidência apresenta uma leitura mais óbvia e uma interpretação alternativa.

### 5.7 Interrogatórios

A função `pintarSuspeitos()` exibe os retratos dos personagens. Quando o jogador escolhe um suspeito, `pintarSala()` monta a conversa e apresenta sugestões de perguntas.

A função `enviar()` registra a pergunta do jogador e chama `responder()`.

A função `responder()` tenta consultar um serviço externo de inteligência artificial para produzir uma resposta dentro da personalidade do personagem. Se essa chamada falhar, a função `reserva()` fornece uma resposta fixa para que o jogo continue funcionando.

Em uma versão publicada, essa chamada de inteligência artificial deveria ser transferida para o backend. Colocar uma chave de API diretamente no JavaScript do navegador expõe essa chave aos visitantes.

### 5.8 Cálculo dos finais

A função `calcularFinal()` avalia o nível de medo, a quantidade de evidências, a confiança dos personagens e o acusado selecionado. Com base nesses valores, escolhe um dos finais armazenados em `FINAIS`.

## 6. Arquivo `app.py`

O arquivo `app.py` é o backend Python da aplicação. Ele utiliza o framework Flask para criar o servidor web e o módulo `sqlite3` para acessar o banco.

### 6.1 Configuração inicial

`BASE_DIR` identifica a pasta onde o arquivo `app.py` está localizado. `DB_PATH` aponta para o banco:

```python
DB_PATH = BASE_DIR / "doce_amaldicoado.db"
```

A aplicação usa `SECRET_KEY` para proteger a sessão. Em ambiente real, essa chave deve ser definida por variável de ambiente e não deve ficar exposta no código.

### 6.2 Conexão com o banco

A função `conectar()` abre uma conexão SQLite e configura o retorno das consultas como linhas que podem ser acessadas pelo nome da coluna.

A função `inicializar_banco()` executa o comando `CREATE TABLE IF NOT EXISTS`. Assim, a tabela é criada automaticamente sem apagar dados existentes.

### 6.3 Tabela de usuários

A tabela `usuarios` possui os campos:

| Campo | Função |
| --- | --- |
| `id` | Identificador único e chave primária. |
| `nome` | Nome exibido para o usuário. |
| `email` | E-mail de login, único e sem diferenciação entre maiúsculas e minúsculas. |
| `senha_hash` | Hash da senha, sem armazenar a senha original. |
| `criado_em` | Data e hora de criação do cadastro. |

Não existe chave estrangeira porque o banco atual possui apenas uma tabela.

### 6.4 Segurança da senha

No cadastro, `generate_password_hash()` transforma a senha em um hash antes do armazenamento. No login, `check_password_hash()` compara a senha informada com o hash salvo.

Isso significa que uma consulta comum à tabela não revela a senha original do usuário.

### 6.5 Sessão do usuário

Depois do cadastro ou login, o backend grava o identificador do usuário em `session["usuario_id"]`.

A função `usuario_atual()` usa esse identificador para consultar o usuário no banco. O frontend recebe apenas o id, nome e e-mail. O hash da senha nunca é enviado ao navegador.

As configurações de cookie usadas são:

- `HTTPOnly`, para impedir acesso ao cookie por JavaScript comum;

- `SameSite=Lax`, para reduzir riscos de requisições cross-site;

- `Secure`, que deve ser ativado quando a aplicação estiver usando HTTPS.

### 6.6 Rotas da API

| Método e rota | Função | Resposta principal |
| --- | --- | --- |
| `GET /api/sessao` | Verifica a sessão atual. | Dados do usuário ou `null`. |
| `POST /api/cadastro` | Valida e cria um usuário. | Usuário criado ou mensagem de erro. |
| `POST /api/login` | Confere e-mail e senha. | Usuário autenticado ou erro 401. |
| `POST /api/logout` | Limpa a sessão. | `{ "ok": true }`. |

### 6.7 Entrega dos arquivos do site

A rota `/` entrega o arquivo `index.html`. A rota `/<path:arquivo>` entrega os arquivos estáticos, como CSS e JavaScript.

Por isso, durante o desenvolvimento, é possível abrir o site pelo próprio Flask sem configurar outro servidor para o frontend.

## 7. Arquivo `requirements.txt`

O arquivo contém a dependência principal do backend:

```
Flask>=3.0,<4.0
```

O Flask fornece o servidor e as rotas HTTP. O SQLite já faz parte da biblioteca padrão do Python, portanto não precisa ser instalado separadamente.

## 8. Como executar no Windows

No PowerShell, dentro da pasta `doce-amaldicoado-separado`, podem ser usados diretamente os executáveis do ambiente virtual:

```
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe app.py
```

Essa forma funciona mesmo quando o PowerShell bloqueia a execução de `Activate.ps1`.

Depois, o site fica disponível em:

```
http://127.0.0.1:5000
```

O banco `doce_amaldicoado.db` é criado na pasta principal do projeto quando o backend é iniciado.

## 9. Testes realizados

Foram testados os principais fluxos da aplicação:

1. Instalação das dependências.

1. Verificação da sintaxe do Python.

1. Verificação da sintaxe do JavaScript.

1. Criação de um cadastro.

1. Recuperação da sessão ativa.

1. Rejeição de senha incorreta.

1. Logout.

1. Consulta do usuário diretamente na tabela `usuarios`.

O cadastro foi armazenado corretamente no SQLite. O teste também confirmou que a senha não aparece na consulta, pois o banco guarda apenas o hash.

## 10. Limitações atuais e melhorias possíveis

A aplicação está adequada para desenvolvimento local e demonstração. Para uma publicação real, seria importante definir uma `SECRET_KEY` forte, usar HTTPS, ativar cookies seguros, desativar o modo de depuração e utilizar um servidor de produção.

O progresso do jogo ainda é salvo somente no `localStorage`. Assim, ele não é sincronizado entre computadores ou navegadores. Uma evolução possível seria criar uma tabela de progresso relacionada à tabela `usuarios` por uma chave estrangeira `usuario_id`.

Também seria recomendável mover a integração com o serviço de inteligência artificial para o backend, protegendo qualquer chave de API e evitando que ela fique visível no navegador.
